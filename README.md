# NU40DK Doom

"Doom runs on everything" 밈을 NU40DK 로. 두 갈래가 한 저장소에 같이 있다.

| | 무엇 | 연산 주체 | 쓰임 |
|---|---|---|---|
| **B안 (메인)** | 보드 단독 3D 엔진 (레이캐스터) | **NU40DK 혼자** | 제품 성능 증명 |
| **A안 (훅)** | 진짜 Doom 1 셰어웨어 | 맥 (보드는 화면+컨트롤러) | 영상 오프닝 시선 잡기 |

영상 구성: A안으로 진짜 Doom 화면을 먼저 보여주고 → "이건 맥이 돌리는 것" →
맥 케이블을 끊고 → B안이 보드 전원만으로 계속 돌아간다.

---

## 왜 원본 Doom 은 보드 혼자 못 돌리나

숫자가 답이다. NU40DK 는 스케치 플래시 **815,104 바이트**, RAM **237,568 바이트**,
Cortex-M4F **64MHz 단일코어**다 (`boards.txt`).

- `DOOM1.WAD` 셰어웨어 하나가 **4,196,020 바이트**. 플래시의 5배가 넘어 게임 데이터를 둘 자리가 없다.
- 원본 Doom 은 4MB RAM 을 전제로 만들어졌다.
- MCU Doom 의 최고 기록인 RP2040 포트조차 **외장 2MB 플래시 + 듀얼코어 오버클럭 + 렌더러 전면 재작성**으로 겨우 했다.
- `variant.h` 에 QSPI 핀(P0.17~P0.23)이 정의돼 있지만 **외장 플래시 칩이 실장돼 있는지는 미확인**.
  달려 있어도 64MHz 단일코어로는 원본 포팅이 비현실적이다.

그래서 B안은 "Doom 원본"이 아니라 **Doom 방식의 3D를 보드가 직접 계산**한다.
주장하는 내용이 전부 사실이라 반박당할 데가 없다는 게 이 선택의 핵심이다.

## B안 — 보드 단독 3D 엔진

```
firmware/nu40_doom/
  nu40_doom.ino    하드웨어 연결 (OLED / 조이스틱 / 버튼 / LED)
  raycast.h .c     3D 엔진 본체. 하드웨어를 전혀 모른다
  assets.h         맵·텍스처·스프라이트 (자동 생성, 직접 고치지 말 것)
tools/
  make_assets.py   ASCII 그림 -> assets.h
  sim/sim.c        raycast.c 를 PC 에서 그대로 컴파일해 프레임을 뽑는다
  sim/sheet.py     정지 화면 대비 시트
  sim/webview.py   브라우저 재생용 preview.html
```

**빌드 결과: 플래시 9% (80,248B), RAM 4% (11,352B).** 3D 엔진 하나가 이 정도다.

### 화면은 보드에 굽지 말고 PC 에서 볼 것

`raycast.c` 는 하드웨어를 안 건드리므로 **보드 펌웨어와 PC 시뮬레이터가 같은 파일을 공유**한다.
PC 에서 본 픽셀이 보드 픽셀과 같다. 굽고 눈으로 확인하는 왕복을 하지 않는다.

```bash
cd tools/sim
clang -O2 -o sim sim.c ../../firmware/nu40_doom/raycast.c -lm

./sim frames.bin 1 900          # 데모 주행 900프레임
python3 sheet.py frames.bin     # 정지 화면 9장 -> sheet.png
python3 webview.py frames.bin   # 브라우저 재생 -> preview.html

# 특정 위치·각도에서 한 장씩 (화면 검사용)
./sim --look 4.5,3.5,0 10.5,13.5,0 16.5,15.5,225
python3 sheet.py look.bin "" look.png
```

`preview.html` 은 **탭을 앞으로 가져와야 30fps 로 재생된다.** 뒤에 있으면 브라우저가
`requestAnimationFrame` 을 초당 1회로 늦춘다 (프레임이 안 넘어간다고 착각하기 쉽다).

### 1비트 화면에서 배운 것

- **바닥은 면을 칠하지 말고 격자선만 그린다.** 체커 무늬를 디더로 칠했더니 노이즈로만 보였다.
  타일 경계선만 원근 투영하면 훨씬 깨끗하고 깊이감이 산다.
- **텍스처는 "어두운 바탕 + 밝은 선"** 으로 그린다. 밝은 픽셀(`#`)을 많이 쓰면 가까운 벽이
  통째로 하얗게 뭉갠다. 처음 그린 텍스처가 전부 그랬다.
- **벽 높이는 화면 높이가 아니라 투영 거리로 나눈다.** `RC_H / dist` 로 쓰면 128x64 처럼
  가로로 넓은 화면에서 벽이 납작해진다. 올바른 값은 `(RC_W/2) / 0.66`.
- **디더는 오더드(Bayer)를 쓴다.** 오차 확산(Atkinson)은 프레임마다 패턴이 튀어서 깜빡인다.

### 프레임레이트

병목은 계산이 아니라 **화면 전송**이다. nRF52840 TWIM 은 400kHz 가 상한이고,
1024바이트 × 9비트 ≈ 24ms 라 **화면만으로 최대 41fps**다. 렌더링은 그보다 훨씬 빠르다.
실측값은 펌웨어가 화면 좌상단과 시리얼(`FPS|`)에 찍는다.

> SPI 방식 SSD1306 모듈을 쓰면 전송이 1ms 대로 떨어져 프레임레이트가 크게 오른다.

### 실측 (2026-08-20, 실물 NU40DK)

**A안 (진짜 Doom 스트리밍): 25 FPS, 보드 응답 없음 0회.**
흐름 제어(보드가 `0x4B` 를 보내야 다음 프레임을 보냄)가 실물에서 정상 동작. 프레임 찢어짐 없음.
호스트에 초당 프레임 카운터를 붙여서 잰 값이다 (`doomgeneric_nu40.c` 의 `DG_DrawFrame`).

> `lsof` 의 `0t...` 오프셋으로 전송량을 재려고 했다가 음수가 나왔다.
> 시리얼 포트에서 그 값은 누적 바이트 수가 아니다. 재려면 호스트에 카운터를 박아야 한다.

**B안 (보드 단독 3D 엔진): 24 FPS.**

### 실물에서 하루 만에 드러난 함정들 (2026-08-20)

- **둠 메뉴는 ENTER 로 안 열린다. ESC 로만 열린다** (`m_menu.c` 의 `key_menu_activate`).
  그래서 타이틀에서는 4번 버튼이 ESC 를, 메뉴가 열린 뒤에는 ENTER 를 보내도록 갈랐다.
  `g_menu_open()`(menuactive) 과 `g_menu_active()`(menuactive || 데모화면) 을 구분해야 한다.
- **`D_StartTitle()` 은 메뉴를 안 닫는다.** 리셋했는데 `menuactive` 가 남아 있으면
  버튼 뜻이 어긋나서 그다음 조작이 전부 밀린다. `M_ClearMenus()` 를 먼저 부를 것.
- **`D_DoAdvanceDemo()` 가 `gameaction = ga_nothing` 으로 덮어쓴다.** 리셋 직후에
  새 게임을 걸면 예약된 데모 전환이 그걸 지우고 자기 데모를 튼다.
  새 게임 전에 `advancedemo = false; demoplayback = false;` 로 예약을 취소할 것.
- **전진+발사(2+4)를 조합키로 쓰면 안 된다.** 걸어가며 쏘는 가장 기본 동작이다.
  게임 중 동시에 누를 일이 없는 짝은 좌회전+우회전(1+3) 뿐이다.
- **조합키는 뗄 때 판정한다.** 누르고 있는 동안 판정하면 긴 동작을 하는 도중에
  짧은 동작이 먼저 튀어나온다. 1+3 하나에 0.5초/2.5초 경계로 세 기능을 걸었다.
- **버튼은 극성을 고정하지 말 것.** 부팅할 때 안 눌린 상태를 기준으로 잡고
  "달라지면 눌림" 으로 읽는다 (`btnPressed`). 5초 넘게 눌린 채면 기준값을 다시 잡는다.
- **`Serial` 을 쓰려면 `#include <Adafruit_TinyUSB.h>`** 가 필요하다. 없으면 링크 에러.
- **화면 종류에 따라 흑백 변환 방식을 바꿔야 한다.**
  DOOM 로고는 글자 속이 어둡고 가장자리만 밝은 입체 글자다. 한 가지 밝기로 자르면
  얇은 테두리만 조각조각 남아 글자가 무너진다. **타이틀·메뉴는 국소 적응 임계값**
  (주변 9x9 평균 + 4 보다 밝으면 켬)을 쓰면 D-O-O-M 이 읽힌다.
  반대로 **게임 중에 국소 적응을 쓰면** 전부 윤곽선이 되어 깊이감이 사라진다.
  `g_in_level()` 로 갈라서 자동 전환한다. 비교: `docs/타이틀_로고_4안.png`
- **E1M1 은 시작 방이 비어 있다.** 난이도를 UV 로 올려도(6마리→29마리) 가장 가까운 적이
  851유닛, 방 한두 개 거리다. 촬영용으로는 `P_SpawnMobj` 로 눈앞에 세우는 게 낫다.

촬영용 조작표와 실행 명령은 `촬영_치트시트.md` 에 따로 정리해뒀다.



**24 FPS.** 한 프레임 41.7ms 중

| | 시간 | 비중 |
|---|---|---|
| I2C 화면 전송 (1024B @ 400kHz) | 약 23 ms | 55% |
| 3D 계산 전부 | 약 19 ms | 45% |

화면 전송이 더 크지만 계산도 무시할 수준은 아니다. SPI OLED 로 바꾸면 전송이 1ms 대가 되어
**50fps 대**까지 오를 여지가 있다 (계산 19ms 가 새 상한이 된다).

부팅 직후부터 데모 모드가 도는 것으로 조이스틱 미연결 판정이 동작함을 확인했다
(조이스틱이 꽂혀 있으면 20초 기다린다). 유령 조작 없음.

### 진짜 Doom 을 보드 없이 미리 보기

`host/doomgeneric_capture.c` 는 진짜 Doom 을 돌려서, 보드로 보낼 화면 그대로를 파일에 찍는다.
보드가 없어도 "실제로 어떻게 보이는지" 확인할 수 있다. 변환 로직은 `doomgeneric_nu40.c` 와 같다.

```
cd host && ./setup.sh                       # doomgeneric 내려받기 + 빌드
cd doomgeneric/doomgeneric
make -f Makefile.capture
CAP_FRAMES=1600 ./doom_capture -iwad ../../doom1.wad     # cap_view.bin / cap_full.bin
CAP_DITHER=1 ...                                          # 디더 버전
```

Doom 은 가만히 두면 타이틀 화면 뒤에 **자기 데모(실제 플레이 녹화)**를 재생한다.
입력을 안 넣어도 진짜 플레이 장면이 나온다. 프레임 1110~1560 구간이 E1M1 주행이다.

- **디더보다 임계값(`v > 128`)이 훨씬 잘 읽힌다** — `docs/진짜둠_임계값vs디더.png`
- **화면 전체(200줄)를 보낸다.** 3D 화면만 잘라내면(168줄) 비율은 맞지만 Doom 의 상태바가
  사라진다. 남들이 "둠이다" 라고 알아보는 건 그 상태바다. 세로가 눌리는 대가가 더 싸다.

### 진짜 Doom 을 보드 혼자 돌릴 수 있나 — 실측

원본 WAD 는 4,196,020B, 보드 스케치 한도는 815,104B. 그대로는 안 들어간다. 깎으면?

| | 크기 |
|---|---|
| 원본 doom1.wad | 4,196,020 B |
| E1M1 한 판 + 그 판에 나오는 것만 (소리·음악·타이틀·나머지 8판 버림) | 933,304 B (22%) |
| 위를 덩어리별 zlib 압축 (필요할 때 하나씩 푸는 방식) | **433,020 B (46%)** |
| 참고: 통째로 LZMA | 295,956 B |

**433KB 면 815KB 안에 들어간다.** 엔진 코드(ARM 빌드 대략 250~300KB)를 얹어도 여유가 남는다.
푸는 데 필요한 임시 버퍼는 가장 큰 덩어리 기준 28KB.

**결론: 안 된다. RAM 이 4배 가까이 모자란다.**

`i_system.c` 에 `DOOM_ZONE_KB` 환경변수를 붙여서 힙을 KB 단위로 줄여가며 실측했다:

| 힙 크기 | 결과 |
|---|---|
| 900 KB | 동작 |
| 850 KB | 실패 — `Z_Malloc: failed on allocation of 64040 bytes` |
| 750 KB 이하 | 실패 |

즉 **최소 약 900KB** 가 필요한데 보드 RAM 은 **237,568B** 다. 3.8배 부족하다.
게다가 그 237KB 는 Arduino 코어·USB 스택·I2C 버퍼·스택과 나눠 써야 한다.

터진 할당 64,040B 는 `I_VideoBuffer`(320x200)다. 나머지 ~836KB 는 WAD 덩어리들이
`PU_STATIC` 으로 힙에 올라간 것. 이걸 줄이려면 "필요할 때 플래시에서 읽어 쓰기" 로
메모리 관리를 통째로 다시 짜야 한다 — 튜닝이 아니라 재작성이다.

플래시는 해결 가능했지만(433KB) 그건 쉬운 쪽 절반이었다. **여기서 멈춘다.**

진짜 벽은 플래시가 아니라 **RAM 237,568B** 다. Doom 은 `I_VideoBuffer` 로만 320x200 = 64,000B 를
쓰고, 여기에 존 힙이 더 붙는다.

- **내부 렌더 해상도를 낮추는 건 `-D` 하나로 안 된다.** 해봤다가 화면이 통째로 검게 나왔다.
  `i_video.c` 의 `fb_scaling = s_Fb.xres / SCREENWIDTH` 가 **정수배 확대만** 지원한다
  (160/320 = 0 이 되어 아무것도 안 그려진다). Doom 을 320x200 아닌 해상도로 빌드하는 건 별도 작업.
- 저장 공간만 놓고 보면 **SD 카드**가 제일 싸게 끝난다. WAD 를 깎을 필요조차 없어진다.
  Doom 은 원래 디스크에서 읽어 쓰도록 만들어진 게임이다.

### 조작 — 보드 버튼 4개만으로 끝난다

조이스틱은 **선택 사항**이다. 외부 부품 없이 보드 하나로 다 된다.

| 입력 | 동작 |
|---|---|
| 버튼 1 | 좌회전 |
| 버튼 2 | 전진 (앞에 문이 있으면 자동으로 열림) |
| 버튼 3 | 우회전 |
| 버튼 4 | 발사 |
| 버튼 2+4 | 달리기 |
| 버튼 1+3 | 데모 모드 켜기/끄기 |
| LED 4개 | 체력 게이지 (25 / 50 / 75 / 100) |

화면 아래 12줄은 상태바다 — 왼쪽 체력, 가운데 얼굴, 오른쪽 탄약.
좌상단의 작은 숫자는 실측 FPS다. "보드가 직접 돌린다"의 증거라 일부러 남겨뒀다.

버튼이 물리적으로 어느 순서로 붙어 있는지는 실물을 봐야 안다.
왼쪽부터 좌회전·전진·우회전·발사가 되게 하려면 `.ino` 의 `BUTTON_PINS` 배열 순서만 바꾸면 된다.

조이스틱을 꽂으면 상/하 = 전진·후진, 좌/우 = 회전이 추가된다. 버튼과 같이 써도 된다.

**데모 모드**: 20초 동안 조작이 없으면 자동으로 켜진다. 웨이포인트를 따라 스스로 돌아다니며
문을 열고 적을 쏜다. 촬영·전시용. 버튼을 누르면 즉시 조작 모드로 돌아온다.
조이스틱이 안 꽂혀 있으면 부팅 즉시 데모 모드로 시작한다.

## A안 — 진짜 Doom 1 (맥이 돌리고 보드가 그린다)

```
host/
  setup.sh              doomgeneric 내려받고 빌드까지
  doomgeneric_nu40.c    플랫폼 레이어 (화면 축소 + 시리얼 송수신)
  health_shim.c         Doom 내부 체력값을 꺼내는 다리
  Makefile.nu40
firmware/nu40_doom_screen/  보드 쪽 (받은 그림을 그리고 입력을 돌려보낸다)
```

```bash
cd host && ./setup.sh
./doomgeneric/doomgeneric/doom_nu40 -iwad doom1.wad
# 포트 지정:  NU40_PORT=/dev/cu.usbmodemXXXX ./...
```

`doom1.wad` 는 id Software 가 무료 배포를 허용한 셰어웨어다. `setup.sh` 가 받는 곳을 안내한다.

### 프로토콜

```
PC   -> 보드 : 0xA5 0x5A, 체력 1바이트, 프레임 1024바이트
보드 -> PC   : 0x49 'I', 입력비트 하위, 입력비트 상위
보드 -> PC   : 0x4B 'K'   <- 다 그렸다. 이걸 받아야 다음 프레임을 보낸다
```

**`K` 흐름 제어가 없으면 화면이 찢어진다.** 맥이 보드보다 빨라서 보드 수신 버퍼가 넘친다.
호스트는 최대 300ms 만 기다린다 (보드를 뽑아도 게임이 멈추지 않게).

### 화면 변환에서 배운 것

- **하단 상태바 32픽셀을 잘라낸다.** 남는 320x168 은 1.90:1 이라 128x64(2.0:1)에 거의 왜곡 없이 들어간다.
  잘라낸 체력은 보드 LED 게이지로 보낸다.
- **프레임마다 자동 대비 보정이 필수다.** 안 하면 Doom 의 어두운 방이 통째로 새까맣게 나온다.
  히스토그램 위아래 3%를 버리고 남은 구간을 편다.
- **1비트 변환은 디더보다 단순 임계값이 잘 읽힌다.** 실제 OLED 는 픽셀 사이 격자가 있어서
  디더 패턴이 더 지저분해 보인다. `doomgeneric_nu40.c` 에 디더로 바꾸는 한 줄이 주석으로 있다.

`docs/A안_진짜Doom_디더링비교.png` 가 실제 Doom 프레임으로 만든 임계값/Bayer/Atkinson 비교다.

## 전원 — 케이블을 뽑으면 꺼진다

B안의 핵심 연출("케이블 없이 돈다")을 하려면 보드에 따로 전원이 필요하다.

1. **리튬 배터리** — `variant.h` 에 `PIN_VBAT`(P0.31)이 있어 배터리 구동을 전제한 설계로 보인다.
   보드에 2핀 JST 커넥터가 실장돼 있는지 **실물 확인 필요.** 있으면 완전 무선.
2. **USB 보조배터리** — 커넥터가 없어도 된다. 처음부터 보조배터리로 전원을 주고
   맥과의 데이터 연결만 끊는다.

손바닥에 올려놓고 들고 다니면서 3D 가 도는 그림이 케이블 뽑는 컷보다 낫다.

## 함정 모음

- **`raycast.h` 의 `extern "C"` 를 지우지 말 것.** `raycast.c` 는 C, `.ino` 는 C++ 로
  컴파일돼서 이게 없으면 링크에서 함수를 못 찾는다.
- **조이스틱을 안 꽂으면 A0/A1 은 뜬 핀이다.** 값이 제멋대로 흔들려 데드존을 넘고,
  유령 조작이 되어 데모 모드가 계속 풀린다. 부팅할 때 흔들림 폭(<120)과 중앙값 위치로
  꽂혔는지를 판정하고, 없으면 아날로그를 아예 읽지 않는다.
- **조이스틱은 반드시 3V3 에.** VRx/VRy 는 VCC 분압이라 5V 를 물리면 ADC 입력 범위를 넘긴다.
- **밝기는 `RC_LIGHT` 하나로 조절한다** (`raycast.c`, 1=어둡게 2=중간 3=기본·밝게).
  밝힐수록 오히려 화면이 **깔끔해진다**. 어두우면 벽이 흩뿌린 점(외톨이 점 48%)으로 보이고,
  밝으면 점들이 뭉쳐 면과 선이 된다(34%). 대신 잃는 건 **거리감**이다 —
  2칸 앞 벽과 8칸 앞 벽의 밝기 차가 안1은 4.9배, 안3은 2.0배로 줄어든다.
  바닥 격자선만은 항상 제곱 감쇠(`atten_floor`)를 쓴다 — 먼 바닥까지 밝히면 선이 뭉친다.
  비교 이미지: `docs/밝기_3안_비교.png`, `docs/밝기_적_비교.png`
- **"둠처럼 보이게" 하는 건 색이 아니라 화면 구성이다.** 진짜 둠을 128x64 1비트로 줄여도
  둠으로 보인다(`docs/A안_진짜Doom_디더링비교.png`). 알아보게 만드는 건 셋이다:
  ① 하단 상태바(체력·얼굴·탄약) ② 화면 하단 중앙의 총 ③ 천장이 있는 실내.
  그래서 화면을 3D 뷰 52줄 + 상태바 12줄로 나눴다. 둠 원본도 상태바가 화면의 16%다.
  전후 비교: `docs/둠느낌_전후비교.png`
- **천장은 바닥보다 훨씬 어둡게 그린다** (`a * 2 / 5`, 선 굵기 상한도 0.12).
  같은 세기로 그리면 위아래 격자가 서로 싸워서 화면이 낙서처럼 된다.
- **얼굴은 13x11.** 눈썹 줄과 눈 줄을 붙이면 하나로 뭉쳐서 고글처럼 보인다. 한 줄 띄울 것.
  체력 34/70 을 경계로 3단, 쏘는 순간에는 인상 쓴 얼굴로 바뀐다.
- **기둥(TALL_TILE=4)은 벽 높이 1.75배.** 벽 높이가 전부 같으면 울펜슈타인처럼 보인다.
  단, 낮은 벽은 못 만든다 — 넘어다보려면 레이를 한 번 더 쏴야 해서 구조가 달라진다.
- **큰 면적에 줄무늬 텍스처를 쓰지 말 것.** 기둥에 경고 줄무늬를 넣었더니 눈이 아팠다.
  세로 홈 + 가로 띠로 바꾸니 기둥으로 읽힌다.
- **적 스프라이트에는 검은 테두리 한 겹을 강제로 그린다.** 밝기를 올리면 흰 벽 앞에서
  적의 실루엣이 벽에 먹혀 사라진다. 투명 픽셀 중 불투명 이웃이 있는 것만 `px_off` 한다.
- **조이스틱 중앙값은 부팅 때 실측한다.** nRF52840 의 기준 전압이 3.6V 라 3.3V 구동 시
  중앙이 2048 이 아니다. 보드·모듈마다도 다르다.
- **`assets.h` 를 직접 고치지 말 것.** `tools/make_assets.py` 의 ASCII 그림을 고치고 다시 돌린다.
- **컴파일할 때 뜨는 `USE_TINYUSB redefined` 경고는 보드 코어 자체의 것**이다. 우리 코드와 무관.
